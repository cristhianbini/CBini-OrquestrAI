# Glossary — CBini OrquestrAI

🇺🇸 **English** · 🇧🇷 [Português](glossary-br.md) · 🇪🇸 [Español](glossary-es.md) · [README](../README.md)

Plain-language definitions of the terms used in this documentation.

| Term | What it means |
|---|---|
| **Cockpit** | The web interface where the operator works: projects, chat, proposals, costs, status. |
| **Operator** | The person using OrquestrAI and making the decisions. |
| **Project** | The unit of work and of isolation. It has its own files, conversation, memory, executions, previews and costs. Other projects cannot see it. |
| **Chat** | Where you talk to the AI about the active project. The chat can read and propose; it never executes. |
| **Model / provider** | The AI model that answers (and the company that runs it). Models can be switched; the project's context stays with the project. |
| **Agents** | Specialized AI roles — strategy, architecture, code, review, testing, documentation — each routed to a model. |
| **Agent mesh / planner** | The team of agents for a task. The planner decides which agents a task needs; the others are skipped and cost nothing. |
| **Command block** (*BLOCO*) | A proposed change, shown first as a plain-language summary (goal, data, files, effect) and then as the full code. Nothing in it runs until approved. |
| **LAVE** | The review routine for every command block: **L**er (read), **A**valiar (evaluate), **V**erificar (verify), **E**xecutar (execute). The name comes from the Portuguese. |
| **Explain** | Asks for a plain-language explanation of a block without running anything. |
| **Veto** | Rejects a version of a block permanently; the reason feeds the next plan. |
| **Execution** | Running an approved block, in an isolated environment that sees only that project. |
| **Revert** | Undoing a supported change, after showing what will be undone. The revert is itself recorded and can be redone. |
| **Factory** | Turns a short brief into a project: Plan → Build → Review → Generate → Publish, with progress visible to the operator. |
| **Static website** | A project made of HTML, CSS and JavaScript, generated by the Factory and changed through command blocks. |
| **Full-stack application** | A web app with interface, API and SQLite database, generated from a tested template, running without network access, evolving through additive changes. |
| **Preview** | Where a generated site or application opens, on a separate origin from the cockpit. |
| **Publication** | Putting a new version of a full-stack application online; automatic after an approved change, keeping the previous version if the new one fails. |
| **Quarantine** | Where a deleted project goes: out of use and out of the list, not destroyed. |
| **Lessons** | Knowledge the system proposes from its own work; it reaches the agents only after a person approves it. |
| **Control plane / execution plane** | Where people and agents decide (control) versus where changes actually happen (execution). |
| **Independent review** | A read-only technical audit of sensitive changes, by a reviewer that did not write them. A blocking finding stops promotion. |
| **Human gate** | A decision point that only a person can pass, such as approving an execution or promoting a capability. |
| **Available / Configurable / Planned** | Maturity labels. *Available* means proven by automated tests and by a person on a live deployment. |
| **Self-hosted** | Installed on infrastructure the organization controls. Content sent to external AI providers still follows their terms. |
